# Decisions

Product decisions made by the owner, and design decisions the lead made while reviewing the slice documents. Newest decisions are added at the end with the next number. Technical decisions go in ADRs (`docs/adr/` for decisions that span slices, `src/<slice>/docs/adr/` for one slice), written with the Technical Proposal.

## Owner decisions

| ID | Date | Decision |
|---|---|---|
| D1 | 2026-11-17 | **The owner's go.** The agent asks in any form (a list, numbered drafts). The go is the owner's reply that clearly identifies which drafts it approves. A reply that does not is not a go, and the agent asks again. One reply may approve several drafts only if it identifies each one; each gets its own approval entry with the owner's words. |
| D2 | 2026-11-17 | **Orders.** An order is recorded only after a go under D1. The owner's own command about an order ("mark Juan's order delivered") is the go for that change. |
| D3 | 2026-11-17 | **Inbox window.** Only customer messages from the last N days count as pending. N is the owner's setting, default 7 days, up to what the provider holds. Older messages stay available as history. |
| D4 | 2026-11-17 | **Inbox groups.** Each pending chat is in exactly one group: needs the owner, then orders, then easy questions. The agent judges the group; when unsure, "needs the owner". |
| D5 | 2026-11-17 | **Notices.** Counts only: no customer text, no names. They cover new messages and chats still unanswered, except chats the owner asked to ignore. Ignoring is an explicit owner command and can be undone. Batching default 10 minutes. While unanswered chats exist, a reminder is sent even with no new messages, default every 30 minutes, separate from batching; the owner can change or pause it. |
| D6 | 2026-11-17 | **Credentials.** The owner enters provider keys and secrets outside the agent conversation, never in the chat. |
| D7 | 2026-11-17 | **Principle 8.** Data stays on the owner's machine unless the owner chooses their own spreadsheet. |
| D8 | 2026-11-17 | **Answering from the phone (UC-4)** is covered by the agent's own remote access; it is not a slice. |
| D9 | 2026-11-17 | **Learning: open.** Nothing is learned without the owner's ok, and each learned item links to the chat and draft it came from. How facts, tone and one-customer cases are told apart is still to design (Knowledge slice). |
| D10 | 2026-11-17 | **Media in v1.** Deputy stores that a media message arrived and its type. If the provider gives a transcript, it is shown as customer text. |
| D11 | 2026-11-17 | **Known limit.** Deputy offers no way to send except an approved draft. An agent with other tools could bypass Deputy; the documents say so instead of claiming it is impossible. |
| D12 | 2026-11-17 | **Receiving.** By default Deputy checks the provider when the session opens and then periodically while it is open (default every 2 minutes, minimum 1). No public address is needed. Live delivery is an optional advanced setting. Setup asks the owner which mode they want and explains the difference. |
| D13 | 2026-11-17 | **Document chain.** After the FRDs comes a cross-cutting TP, then 1..N TPs per FRD with an ADR for each choice, then one spec per FRD, then implementation with ATDD. The FRDs' Given/When/Then tests are acceptance criteria. |
| D14 | 2026-11-17 | **Architecture.** Ports and adapters (hexagonal) with DDD and clean architecture. Each slice is a bounded context with domain, application, ports and adapters; a composition root wires them; an architecture test enforces the dependency rule. The previous code's structure is not kept. |
| D15 | 2026-11-17 | **Order scrub (L6).** The drafts log only grows, with one narrow, tested exception: deleting an order replaces the owner's words in its entries with "deleted". |
| D16 | 2026-11-17 | **Second session.** A session that is not the owner is read-only: it cannot create drafts, approve or send. |
| D17 | 2026-11-17 | **Packaging.** v1 ships as a compiled binary, so the owner does not need Bun installed. The package name is decided before launch. |
| D18 | 2026-11-17 | **First live agents.** Live checks (stdio idle timeout, server instructions) run first on Claude Code, then Codex. |
| D19 | 2026-11-17 | **Sensitive settings.** Provider, receiving mode, push and secrets change only through the owner's own terminal command, never through an agent tool. Setup shows the command, waits, and confirms the result. |
| D20 | 2026-11-17 | **Language.** Deputy speaks to the agent in fixed codes with an English default; the agent says them in the owner's language. Deputy ships no per-language text catalogs. |
| D21 | 2026-11-17 | **Currency.** Setup suggests the currency from the owner's country and the owner confirms it; a catalog column may override it per product. |
| D22 | 2026-11-17 | **Catalog import.** Deputy detects the separator, number format and which column is which, and shows the owner the mapping to confirm once. |
| D23 | 2026-11-18 | **Pending after "ok".** A short reply such as "ok" or "thanks" after an answer does not make a chat pending when the agent is sure the chat is closed. When it is not sure, it asks the owner. |
| D24 | 2026-11-18 | **Ignored chats.** By default an ignored chat stays ignored until the owner removes it. Later, outside setup, the owner can configure exceptions, for example a mention in a group, and an expiry. |
| D25 | 2026-11-18 | **Drafts across sessions.** A draft that was not approved still waits in the next session, marked as from an earlier session. The send path re-checks the chat as for any draft. |
| D26 | 2026-11-18 | **Order defaults, configurable later.** By default: the delivery date is optional, status changes are free, the total is computed from the items, and an export leaves cancelled orders out. Each of these becomes an owner setting later. |
| D27 | 2026-11-18 | **Natural approval of lessons.** The agent proposes a lesson in plain words with its kind (for example: "here *pesos* means córdobas, so 20 pesos is written C$20", kind currency). The owner answers in their own words, not only "yes"; no number is needed. The agent reads the answer, using what it has learned of how the owner speaks. When in doubt, it asks. Deputy itself checks only its own state: a bare approval counts only when exactly one lesson is waiting and the agent just showed it; otherwise the agent asks which one. Lessons about how Deputy answers on the owner's number (prices, currency names, wording) are the main case. |
| D28 | 2026-11-18 | **Name length.** A customer name is capped at 80 graphemes by default; the cap becomes an owner setting later. |
| D29 | 2026-11-18 | **Rate limit (429).** An approved send that gets a 429 waits in a queue per customer chat, so a hold in one chat never stops the others. It is retried at the time the provider gives. Before the retry, every pre-send check runs again (new customer message, owner reply from the app, draft changed); if anything changed, Deputy holds and asks the owner again. If the retry time falls outside WhatsApp's 24-hour customer window, the send fails at once and the owner is told. |
| D30 | 2026-11-18 | **Unattributed owner reply.** An owner reply that Deputy cannot tie to a chat holds every send, and the notice says clearly why and what the owner must do. |

## Lead decisions (design, from the reviews)

| ID | Date | Decision |
|---|---|---|
| L1 | 2026-11-17 | Setup installs Deputy into the agent first, in test mode, so its checks exist from step 1. Test mode skips the provider steps. |
| L2 | 2026-11-17 | A message from the owner's number is "sent through Deputy" only when it matches one of Deputy's send identifiers. Anything else from the owner's number is "owner from the app". A wrong "owner" label only holds a send; the other mistake would answer over the owner. |
| L3 | 2026-11-17 | Dev test messages never count as pending, notified or draftable once the provider is not dev. |
| L4 | 2026-11-17 | The ignore list (owned by Inbox) and the owner numbers change only by an explicit owner command, logged with the owner's words, and the owner can list them at any time. |
| L5 | 2026-11-17 | Reply drafts and order drafts share one numbering. A chat may have one waiting reply draft and one waiting order draft. |
| L6 | 2026-11-17 | Order entries in the drafts log keep the owner's words while the order exists. Deleting an order replaces them with "deleted", so no personal data remains. |
| L7 | 2026-11-18 | Gaps the Drafts specs found in the Drafts TPs. A quota failure maps to `fail_rejected`, with reason "quota" in the log. A queued send is logged as `sending` with reason `send_queued`. Times in codes are ISO UTC, and the agent renders them in local time (D20). `SendNeedsOwner` gains the reason `retry_failed`. The log port gains `approvalEntryIdFor` and `hasOrderDeleted`. `RetrySend` reuses the approve pipeline. An order command reads the order's chat from Orders (`chatOf`) before it logs. |
| L8 | 2026-11-18 | Gaps the Intake specs found in the Intake TPs. `chats` and `messages` gain `provider_sender` and `provider_id`. A message that matches a Deputy send is never unattributable. Signals that another slice consumes live in `src/shared/signals.ts`. Tools that compose several slices (`status`, `get_settings`, `set_setting`, `list_drafts`, the lesson tools) live in `src/composition/mcp/`; that folder holds the MCP server and its instructions, may import any slice's inbound ports and `src/adapters/`, and only `src/main.ts` imports it. Each slice's own tools live in `src/<slice>/adapters/mcp/`; `src/adapters/mcp/` holds only shared MCP code (`ToolDefinition`, the customer-text helper). Kapso field paths not confirmed by Kapso's docs are launch gates. |
| L9 | 2026-11-18 | Choices the Drafts specs make where the Drafts TPs are silent. `answers` is a `MessageId` or null. `retry_at` and `attempts` are columns of `drafts`. `ChangeDraft` and `RejectDraft` parse the owner's words (1 to 1,000 characters) and refuse `words_empty`. Orders' refusal text becomes `failReason`. A delete logs "delete" and a refused order command logs `order_command_failed`. `hasDraftText` matches the scrubbed "deleted" text. `messagesSince` returns dev and real messages, and the freshness policy filters them. `RetryPendingOutcomes` is the 10-second retry of a failed outcome write. A log `limit` outside 1 to 100 is `bad_limit`. `stuckDrafts` lists reply drafts only. A field that does not fit the draft kind on `change_draft` is `wrong_kind`. `INSTRUCTIONS` carries one short sentence on the known limit and stays within 512 characters. `order_outcome_unknown`, `session_ended`, `found_after_unknown` and `order_command_failed` get default texts. `RecoverInterrupted.redriven` only counts. `unknown_outcome` covers unknown results that are not split sends. A failed outcome write other than `sent` returns `log_unavailable`. `OnOrderDeleted` refuses `not_owner` outside the owner process. The `sent` write is tried at 0, 1 and 3 seconds. |
| L10 | 2026-11-18 | Choices made during the build of the foundation. When a domain function needs data that a port also carries, the domain defines its own input type with only the fields it reads, and the port's type satisfies it structurally, checked at type level in the unit test (ADR-000: the domain never imports a port). A released lease is free at once, and an expired one is free at exactly 30 seconds (`heartbeat = 0 OR heartbeat <= now - 30000`). The `adapter-instantiated` rule flags `new X(` only for a class imported from an `adapters/` path. `readConfigFile` and `SecretStore` are built in Intake SPEC-01 Task 7, not Task 6. The start-up check reports missing Kapso items before a bad `receiving_mode` (TP-01 rule order), and an empty secret counts as missing. `main.ts` builds the event bus with the first slice that publishes. `drafts.replaced_by` is `DEFERRABLE INITIALLY DEFERRED`, and a replace saves the old draft before inserting the new one in one transaction, because the open-draft index and the foreign key otherwise refuse both orders (amends Drafts TP-01 line 237). |
